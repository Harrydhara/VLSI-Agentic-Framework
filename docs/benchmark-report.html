One-shot vs. iterative RTL generation

We ran the agent 200 times on ten small circuits with a local model, gemma4:26b, and scored every attempt with a hidden reference test. Round 1 compared one-shot and iterative generation with two prompt strategies. Round 2 tested a different workflow, in which the testbench is written from the specification before the design.

Benchmarks run on 15 October 2026 · held-out runs at commit 99c4655 (round 1) and 63c4a39 (round 2, declared in advance)

The short answer

Revising from the agent's own feedback rarely changed the outcome. Across 200 paired runs, revisions fixed 10 designs and broke 4. Most fixes were compile errors that the tools named by line.

The weak link is the agent's own testbench. On the held-out circuits, every strategy's checks rejected 54–81% of designs that were in fact correct, so most revisions went into designs that were already right.

Round 2 wrote the testbench from the specification first, in a separate conversation. On the dev circuits it cut those false rejections from 51% to 21% and fixed the signed-compare bug in 3 runs, which no round-1 revision managed. On the held-out circuits the gain did not hold: it scored 21/25 and 23/25 against 24/25 and 25/25 for the simpler strategies, and cost the most tokens.

Method

The agent loop

  1. The model gets the circuit's description and exact module header, and writes a design and a self-checking testbench.
  2. Development checks run: compile with Icarus Verilog 12, run the testbench against the design, and synthesize with Yosys 0.57, flagging any latches.
  3. If a check fails, the model gets the problems as text and tries again, up to 3 attempts. The run stops as soon as its checks pass.
  4. After the run, every attempt's design is scored by the circuit's hidden reference test. The model never sees this test or its output, and the loop never uses it.

Paired one-shot and iterative scores

Attempt 1 of a run uses exactly the prompt a one-shot run would use, so each run gives two scores: one-shot is attempt 1's design, iterative is the final design. A run counts as fixed when attempt 1 failed the hidden test and the final design passed, and as broken in the opposite case.

Four strategies

  • default: the starter prompts. One reply contains the design and its testbench.
  • tb_timing: the same, plus advice on testbench timing.
  • spec_first v1: the testbench is written first, from the specification alone, in its own conversation, and must run against a placeholder design. The design is written in a second conversation and never sees the testbench. When a design fails checks, the failing checks go to the testbench's author first, who either corrects the testbench or confirms it.
  • spec_first v2: the same, but the testbench's author must quote the sentence of the specification behind any expected value it changes.

Settings

  • Model: gemma4:26b (25.2B mixture-of-experts, 4-bit quantized) via Ollama 0.31.2 on one RTX 4090.
  • Temperature 0.2, thinking off, at most 4,096 output tokens per reply, 50,000-token budget per run (no run reached it).
  • Seeds 1–5 per circuit and strategy. Runs with the same seed and prompt repeat exactly, so each seed is one independent sample.

How reliable was the agent's own feedback?

Every attempt that produced code was judged twice: by the agent's own development checks and by the hidden reference test. A correct design that fails the agent's checks gets revised anyway. A wrong design that passes them ends the run with a wrong answer.

The cases we inspected traced false rejections to the testbenches: some compared outputs before they settled or at the clock edge instead of just after it, some computed wrong expected values, some failed to compile, and some never printed a result line. Writing the testbench first lowered false rejections on dev (21% and 32%), but not on the held-out circuits (65% and 59%), whose clocked designs and wider ALU were harder to test correctly.

Examples

fixed by revision

1. A compile error the tools named

mux4 · default · held-out seed 1 (seed 4 was the same)

The design assigned to y inside an always block but declared it as a plain output, so Icarus Verilog stopped:

design.v:12: error: y is not a valid l-value in mux4.

That line went back to the model, which changed one declaration. Attempt 2 passed the hidden test, 1064/1064.

-    output [3:0] y+    output reg [3:0] y
never fixed in round 1

2. A logic bug no revision touched

alu8 · default · held-out seed 4

The specification defines SLT as a signed comparison. The model sign-extended both operands and compared them with <:

wire [8:0] sa = {a[7], a};
wire [8:0] sb = {b[7], b};
...
3'b111: y_reg = (sa < sb) ? 8'h01 : 8'h00;   // SLT

Sign extension does not make < signed. Both vectors are still unsigned, so b = −128 becomes 9'h180, which compares as larger than 0. The correct form is $signed(a) < $signed(b). The hidden test caught it:

MISMATCH op=111 a=0 b=128: expected y=0 zero=1 carry=0 overflow=0 negative=0, got y=1 zero=0 ...

The model's own testbench reported 0/23 checks passed with every output shown as x, so its feedback said nothing useful about SLT. All three attempts kept the same comparison.

accepted a wrong design

3. A testbench with the same mistake

alu4 · tb_timing · dev seed 4, attempt 2

The design and the testbench's reference model used the identical comparison. The testbench's comment states the intended result, but its model computes the opposite, the design agrees with the model, and the agent's checks pass.

// design
3'b111: if ({a[3], a} < {b[3], b}) y_reg = 4'h1; else ...
// testbench reference model
3'b111: if ({a[3], a} < {b[3], b}) m_y = 4'h1; else m_y = 4'h0;
// testbench stimulus
op = 3'b111; a = 4'b1111; b = 4'b0001; #1; update_model(); check(); // -1 < 1 -> 1

By its own checks the run ended in success. The hidden test failed it, 1920/2048. The project proposal named this as its biggest risk: generated RTL and a generated testbench sharing one misunderstanding. It motivated round 2.

broken by revision

4. A revision that broke a correct design

alu4 · tb_timing · dev seed 2

Attempt 1 compared correctly through signed wires and passed the hidden test, 2048/2048. Its testbench did not compile, because it wrote negative constants as 4'd-1 instead of -4'd1. Asked to fix the problems, the model rewrote both files. The new design used the unsigned comparison from example 3, and the new testbench agreed with it.

-    y_reg = (a_s < b_s) ? 4'b0001 : 4'b0000;   // a_s, b_s are wire signed+    if ({a[3], a} < {b[3], b}) y_reg = 4'b0001;

The agent's checks passed and the run stopped. The hidden test scored the final design 1920/2048.

tooling bug, now fixed

5. A bug in our own extractor

alu4 · default · dev seed 1

In one reply the model rewrote module alu4 five times and was cut off at the 4,096-token limit. Our extractor joined every version into one file, which failed to compile:

design.v:90: error: 'alu4' has already been declared in this scope.

This first looked like iteration fixing a compile error. The extractor now keeps the last complete definition of a repeated module (commit 2fcb7fb), and with that the reply's final version passes the hidden test. This was the only run affected.

gave in to the bug

6. A testbench author that gave in

alu4 · spec_first v1 · dev seed 2

This time the testbench was written first and was right. The design, written separately, had the same signed-compare bug as example 2 and failed 128 of the testbench's 2,048 checks. Asked to review those checks, the testbench's author rewrote its expected values to match the design. The recheck passed 2048/2048 and the run ended. The hidden test failed the design, 1920/2048.

v2 was written to stop this: its author must quote the specification before changing a value. On the same circuit and seed, v2's author kept its testbench twice and the design was fixed on attempt 3.

kept a wrong testbench

7. Right values, wrong moment

counter4 · spec_first v2 · dev seed 2

The design was correct, but the testbench sampled the count at the clock edge, before the design had updated it. Asked to review, the author quoted the specification correctly:

FAIL: rst=0, en=1, clk_edge=rising. Expected count= 1, Actual count= 0
- Quoted sentence: "otherwise, if en is 1, count increases by 1, wrapping from 15 back to 0"
- Required value: (previous_count + 1)
- My testbench's expected value matches it.

The expected values were right; the time at which they were compared was wrong, and quoting the specification cannot reveal that. The author kept its testbench, the correct design was revised twice to match it, and the final version failed the hidden test. Most of v2's 28 wrong "keep" decisions looked like this.

prompt side effect

8. A side effect of the design-only prompt

seqdet_mealy · spec_first v1 and v2 · held-out

In 7 of the 10 spec_first runs, the first design drove the Mealy output inside a combinational block while declaring it a plain output, the same mistake as example 1:

output detected
...
always @(*) begin
    next_state = S0;
    detected = 1'b0;    // error: detected is not a valid l-value

With the default prompts, which ask for design and testbench in one reply, the model wrote assign detected = ... and all 5 designs compiled. The design rules in the two prompts are word-for-word the same, so this comes from how the request is framed. It is the main reason spec_first's one-shot scores are lower, and most of these runs were fixed later from the compiler's message.

tooling bug, now fixed

9. A parser bug in our own framework

counter4 and mux2 · spec_first v1 · dev

Some generated testbenches miscounted and printed a negative pass count. Our parser only accepted non-negative numbers, so it told the model the testbench "printed no RESULT line", which was false:

RESULT: -15/23 passed

In spec_first this made all five counter4 testbenches "unusable", so those runs fell back to compile and synthesis checks with no functional test at all. Negative counts now parse and can never count as a pass (commit 5f424b4). The 8 affected dev runs were re-done; no held-out run was affected.

Difficulty check

The first six circuits turned out too easy: the model passed nearly all of them in one shot, which would leave nothing for iteration to improve. Four harder circuits were added and checked with one-shot runs on seeds 101–105, before any benchmark.

Caveats

  • Small samples. Each strategy has 25 runs per split, so differences of 1–3 runs are within noise. For example, 22/25 vs. 25/25 one-shot on the held-out set gives p ≈ 0.23 with Fisher's exact test, and the strategies' order flips between dev and held-out.
  • One logic bug dominates. Most logic failures were the ALUs' signed comparison. Conclusions about which logic bugs iteration can fix rest mostly on that one bug type.
  • One model and one setting. All runs use gemma4:26b at temperature 0.2. Other models, or a higher temperature, may revise differently.
  • Small circuits. At most 8 bits and 5 states. Larger designs give the tools more to report and the model more to get wrong.
  • Strategies change the first prompt too. tb_timing's and spec_first's one-shot results differ from default's partly because their prompts differ (example 8), so the comparison is not a pure test of feedback.
  • Bounded evidence. Reference tests are exhaustive for the combinational circuits and directed plus random for the sequential ones. Passing them is strong evidence, not proof.
  • Held-out circuits used more than once. They were used by the difficulty check (one-shot, seeds 101–105), round 1 and round 2 (both seeds 1–5). Strategies were tuned on dev only, and round 2's two versions were declared before their held-out runs.
  • Code changed between rounds. The round-2 refactor was checked by replaying 5 recorded round-1 runs with identical results. The parser fix (example 9) changed one round-1 dev run, which was re-done; the tables show the re-done result.

What to try next

  • A testbench harness from the framework. Provide the clock, reset sequence and sampling time (compare one time unit after the rising edge), and let the model write only the stimulus and the reference model. Most wrong testbenches failed on timing rather than on expected values (example 7).
  • Keep the last design that compiled. Three round-2 runs ended on a final revision that did not compile, although earlier attempts did.
  • Stop when nothing changes. Many runs returned the same design on every attempt while only the testbench changed. Stopping when the design repeats would save most of the extra tokens.
  • More kinds of failure and more samples. Add the planned FIFO pair (pointer wrap-around, full and empty flags), more seeds per circuit, and a second model.

Reproduce

From the project folder inside WSL. Each command skips runs that already exist, so it can be resumed.

vlsi-agent bench --split dev --seeds 1-5 --out runs/bench/dev-seeds1-5 \
    --prompts prompts/default prompts/examples/tb_timing prompts/examples/spec_first_v1 prompts/examples/spec_first
vlsi-agent bench --split heldout --seeds 1-5 --out runs/bench/heldout-seeds1-5 \
    --prompts prompts/default prompts/examples/tb_timing prompts/examples/spec_first_v1 prompts/examples/spec_first
python3 docs/report/build.py        # rebuilds this page from the runs

Each benchmark folder holds summary.md, rows.csv, and every run's files: the model's replies, the designs and testbenches, the feedback it received, and the hidden test's log for each attempt.

Every table and run grid on this page is generated by docs/report/build.py from runs/bench/dev-seeds1-5 and runs/bench/heldout-seeds1-5.
