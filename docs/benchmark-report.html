One-shot vs. iterative RTL generation

We ran the agent 100 times on ten small circuits with a local model, gemma4:26b, and scored every attempt with a hidden reference test. This page reports what revising from tool feedback changed.

Benchmarks run on 15 October 2026 · held-out runs made with the agent frozen at commit 99c4655

The short answer

Revising helped only when the tools named the problem. Across 100 paired runs, revisions fixed 2 designs and broke 1. Both fixes were compile errors that Icarus Verilog reported by line. The one recurring logic bug, a signed comparison computed as unsigned, survived every revision. In the 3 runs that started with it, the agent's own testbench either did not work or made the same mistake, so the feedback never pointed at it.

The agent's own checks are the weak link. They rejected 36–81% of designs that were in fact correct. Those correct designs went back for more revisions, so a full iterative run cost 2.2–4.7 times the tokens of its first attempt.

Method

The agent loop

  1. The model gets the circuit's description and exact module header. It replies with a design and its own self-checking testbench.
  2. Development checks run on that reply: compile with Icarus Verilog 12, run the model's testbench, and synthesize with Yosys 0.57, flagging any latches.
  3. If a check fails, the model gets the problems as text and tries again, up to 3 attempts. The run stops as soon as its checks pass.
  4. After the run, every attempt's design is scored by the circuit's hidden reference test. The model never sees this test or its output, and the loop never uses it.

Paired one-shot and iterative scores

Attempt 1 of a run uses exactly the prompt a one-shot run would use, so each run gives two scores: one-shot is attempt 1's design, iterative is the final design. A run counts as fixed when attempt 1 failed the hidden test and the final design passed, and as broken in the opposite case. Comparing within the same run removes the noise between separate one-shot and iterative runs.

Settings

  • Model: gemma4:26b (25.2B mixture-of-experts, 4-bit quantized) via Ollama 0.31.2 on one RTX 4090.
  • Temperature 0.2, thinking off, at most 4,096 output tokens per reply, 50,000-token budget per run (no run reached it).
  • Two prompt strategies: default, the starter prompts, and tb_timing, which adds testbench timing advice.
  • Seeds 1–5 per circuit and strategy. Runs with the same seed and prompt repeated exactly, so each seed is one independent sample.

  3. One extraction bug was fixed (example 5) and the one affected dev run was re-done. The agent's code was then frozen.
  4. Held-out benchmark: seeds 1–5, never used on these circuits before, both strategies, 50 runs.

How reliable was the agent's own feedback?

Every attempt that produced code was judged twice: by the agent's own development checks and by the hidden reference test. The two disagree in two ways. A correct design that fails the agent's checks gets revised anyway. A wrong design that passes them ends the run with a wrong answer.

Some compared outputs before they settled or saw every output as x, some compared against wrong expected values, some failed to compile, and some never printed a result line.

tb_timing rejected fewer correct designs and used fewer tokens, but its testbenches failed to compile in 10 of 39 dev attempts against 0 of 43 for default, and it was the only strategy whose checks accepted a wrong design. Over both splits the two strategies are close: default 46/50 one-shot and 48/50 iterative, tb_timing 48/50 and 47/50.

Examples

fixed by revision

1. A compile error the tools named

mux4 · default · held-out seed 1 (seed 4 was the same)

The design assigned to y inside an always block but declared it as a plain output, so Icarus Verilog stopped:

design.v:12: error: y is not a valid l-value in mux4.

That line went back to the model, which changed one declaration. Attempt 2 passed the hidden test, 1064/1064.

-    output [3:0] y+    output reg [3:0] y
never fixed

2. A logic bug no revision touched

alu8 · default · held-out seed 4

The specification defines SLT as a signed comparison. The model sign-extended both operands and compared them with <:

wire [8:0] sa = {a[7], a};
wire [8:0] sb = {b[7], b};
...
3'b111: y_reg = (sa < sb) ? 8'h01 : 8'h00;   // SLT

Sign extension does not make < signed. Both vectors are still unsigned, so b = −128 becomes 9'h180, which compares as larger than 0. The correct form is $signed(a) < $signed(b). The hidden test caught it:

MISMATCH op=111 a=0 b=128: expected y=0 zero=1 carry=0 overflow=0 negative=0, got y=1 zero=0 ...

The model's own testbench reported 0/23 checks passed with every output shown as x, so its feedback said nothing useful about SLT. All three attempts kept the same comparison.

accepted a wrong design

3. A testbench with the same mistake

alu4 · tb_timing · dev seed 4, attempt 2

Here the design and the testbench's reference model used the identical comparison. The testbench's comment states the intended result, but its model computes the opposite, the design agrees with the model, and the agent's checks pass.

// design
3'b111: if ({a[3], a} < {b[3], b}) y_reg = 4'h1; else ...
// testbench reference model
3'b111: if ({a[3], a} < {b[3], b}) m_y = 4'h1; else m_y = 4'h0;
// testbench stimulus
op = 3'b111; a = 4'b1111; b = 4'b0001; #1; update_model(); check(); // -1 < 1 -> 1

By its own checks the run ended in success. The hidden test failed it, 1920/2048. The project proposal named this as its biggest risk: generated RTL and a generated testbench sharing one misunderstanding.

broken by revision

4. A revision that broke a correct design

alu4 · tb_timing · dev seed 2

Attempt 1 compared correctly through signed wires and passed the hidden test, 2048/2048. Its testbench did not compile, because it wrote negative constants as 4'd-1 instead of -4'd1. Asked to fix the problems, the model rewrote both files. The new design used the unsigned comparison from example 3, and the new testbench agreed with it.

-    y_reg = (a_s < b_s) ? 4'b0001 : 4'b0000;   // a_s, b_s are wire signed+    if ({a[3], a} < {b[3], b}) y_reg = 4'b0001;

The agent's checks passed and the run stopped. The hidden test scored the final design 1920/2048.

tooling bug, now fixed

5. A bug in our own extractor

alu4 · default · dev seed 1

In one reply the model rewrote module alu4 five times and was cut off at the 4,096-token limit. Our extractor joined every version into one file, which failed to compile:

design.v:90: error: 'alu4' has already been declared in this scope.

In the first dev run this looked like iteration fixing a compile error. The extractor now keeps the last complete definition of a repeated module (commit 2fcb7fb). With that change the reply's final version passes the hidden test, and the dev result for default became 24/25 one-shot and 24/25 iterative, with nothing fixed. This was the only run affected.

Difficulty check

The first six circuits turned out too easy: the model passed nearly all of them in one shot, which would leave nothing for iteration to improve. Four harder circuits were added and checked with one-shot runs on seeds 101–105, before any benchmark.

Caveats

  • Small samples. Each strategy has 25 runs per split, so differences of 1–3 runs are within noise. For example, 22/25 vs. 25/25 one-shot on the held-out set gives p ≈ 0.23 with Fisher's exact test.
  • One logic bug dominates. 4 runs hit the SLT bug: 3 started with it and kept it, and in 1 a revision introduced it. "Iteration never fixed a logic bug" rests mostly on that one bug type.
  • One model and one setting. All runs use gemma4:26b at temperature 0.2. Other models, or a higher temperature, may revise differently.
  • Small circuits. At most 8 bits and 5 states. Larger designs give the tools more to report and the model more to get wrong.
  • Strategies change the first prompt too. tb_timing's one-shot results differ from default's because its prompt differs, so the strategy comparison is not a pure test of feedback.
  • Bounded evidence. Reference tests are exhaustive for the combinational circuits and directed plus random for the sequential ones. Passing them is strong evidence, not proof.
  • Held-out circuits seen once before. The difficulty check ran one-shot on alu8 and seqdet_mealy with different seeds (101–105). No strategy was tuned on them.

What to try next

  • Spec-first testbench. Have the model write the testbench, with its own reference model, from the specification in a separate call before it writes the design. That keeps the testbench from copying the design's misunderstanding, which caused examples 3 and 4.
  • Stop when nothing changes. Many runs returned the same design on every attempt while only the testbench changed. Stopping when the design repeats would save most of the extra tokens.
  • More kinds of failure. Add the planned FIFO pair (pointer wrap-around, full and empty flags) so results do not hinge on the SLT bug.
  • More samples. More seeds per circuit, and a second model, to tell small differences from noise.

Reproduce

From the project folder inside WSL, with the agent at commit 99c4655 or later:

vlsi-agent bench --split dev --seeds 1-5 \
    --prompts prompts/default prompts/examples/tb_timing --out runs/bench/dev-seeds1-5
vlsi-agent bench --split heldout --seeds 1-5 \
    --prompts prompts/default prompts/examples/tb_timing --out runs/bench/heldout-seeds1-5

Each benchmark folder holds summary.md, rows.csv, and every run's files: the model's replies, the designs and testbenches, the feedback it received, and the hidden test's log for each attempt.

Numbers on this page come from runs/bench/dev-seeds1-5 and runs/bench/heldout-seeds1-5. The run grid is generated from each run's history.json.
